Version control that doesn't fight you.

Helix is a rethink of Git built around how teams actually review code. It keeps everything good about Git, fixes what trips people up daily, and treats code review as a first-class part of the tool — not a website bolted on top.

The everyday pain Helix removes

Three things that bite developers — and their managers — every day.

1

"Wait, did the reviewer's comments survive?"

In Git, fixing a typo in a code review can lose the reviewer's place. Helix gives every change a stable identity that survives edits — reviewers see "version 2 of the same change" instead of "a brand-new one."

2

"I think I just lost my work."

Git's history-rewriting tools are powerful and unforgiving. Helix records every action you take and lets you undo any of them — there's no "I broke my repo" moment.

3

"How do I do this again?"

Git has 150+ commands. Helix has 15 daily ones, with names that mean what they do. New developers ramp up in hours, not weeks.

4

"Reviews live in another tool."

In most teams, code lives in Git and reviews live in GitHub or Gerrit. They don't talk well. Helix puts reviews, comments, and approvals into the repository itself — so audits, migrations, and offline work all just work.

Where it stands today

    
Plain-English honesty about what's done and what isn't.

    

      
Working today

      
    
        
  • Every command above runs and produces correct results — 35 automated tests verify behavior on every change.
    • 
        
  • The "magic moment" you saw above is a real property of the tool, not a marketing animation.
    • 
        
  • Anyone with the Go compiler can build and use it locally, today.
    • 
      

      
Not yet ready

      
    
        
  • Network sharing works between two folders on your computer; over-the-internet sharing needs the server piece (designed, not yet built).
    • 
        
  • The web review interface — comments, approvals, the whole "GitHub-like" experience — is in the design document, not yet in code.
    • 
        
  • This is a demo-able prototype, not a production tool. If your team is using Git and shipping software, keep doing that.
    • 
      

    

  


  
  

    
What this is for

    
Three audiences, three reasons to care.

    

      

        
For engineering leaders

        
A working proof that you can fix the everyday friction Git creates without giving up its strengths. Read the design, run the demo, decide if it's worth investing in further.

      

      

        
For developers

        
An honest "what would Git look like if it were designed today" exercise — with code, not just slides. Clone it, break it, send a pull request.

      

      

        
For everyone else

        
A look under the hood at the tools your engineers use 50 times a day, and a peek at where they could go next.
